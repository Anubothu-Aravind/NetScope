# NetScope Architecture Specification

## 1. System Components

### A. Control Plane — FastAPI Web Server (`app/`)
- Built with **FastAPI** + **Uvicorn** + **Segno**. Listens on `0.0.0.0:8000`.
- **Session Manager (`app/session_manager.py`)**:
  - Creates unique sessions prefixed with `NS-` (e.g. `NS-A1B2C3`).
  - Registers connected devices (phone, laptop) with IP, role, and heartbeat.
- **Pairing Manager (`app/pairing_manager.py`)**:
  - Deterministically pairs one `SEND` client with one `RECEIVE` client.
  - Assigns unique `pair_id` (e.g., `P-001`).
  - Manages pair states: `WAITING_FOR_PEER -> PAIRED -> TCP_CONNECTING -> TRANSFERRING -> COMPLETED / FAILED`.
- **Security Middleware (`app/main.py`)**:
  - Remote clients (Wi-Fi) may only access `/join/*`, `/api/session/*`, `/api/qr/*`, and static UI assets.
  - All admin controls (`/api/impair`, `/api/transfer`, `/api/experiments/*`, `/api/upload`) are loopback-only (`127.0.0.1`).

### B. Data Plane — TCP Transfer (`client/`)
- Direct peer-to-peer TCP channel on **port 5000**.
- **`client/tcp_sender.py`**: Streams 64 KB chunks; computes SHA-256 in real time; times total transfer.
- **`client/tcp_receiver.py`**: Writes chunks; verifies SHA-256 checksum; returns confirmation.
- These are the **canonical** transfer classes. `server/tcp_server.py` is legacy kept for backward-compatibility with `tests/test_transfer_localhost.py`.

### C. Single-Laptop Namespace Testbed (`network/`)
The project emulates a two-machine setup using Linux network namespaces.

```
HOST MACHINE (one laptop)

  ns-client  (10.10.0.1)          ns-server  (10.10.0.2)
  +---------------------------+    +---------------------------+
  |  tcp_sender.py  ----------+----+-> tcp_receiver.py        |
  +---------------------------+    +---------------------------+
         veth-c  <---------------------> veth-s
           |
      [tc netem]  (delay / loss / bandwidth limit)
      [tshark]    (packet capture for analysis)
```

- **`network/netns_setup.sh up|down|status`**: Creates/destroys namespace pair; disables NIC offloads.
- **`network/nsrun.sh NS CMD`**: Executes `CMD` inside namespace `NS` via `ip netns exec`.
- **`network/impair.sh`**: Applies/clears `tc netem` rules on `veth-c`.
- **`network/scenarios.json`**: The 11 specification scenarios.
- **`network/install_sudoers.sh`**: Installs `/etc/sudoers.d/netscope` for passwordless experiment runs.

### D. Traffic Control & Packet Capture
- `network/impair.sh` applies `tc netem` rules to `veth-c` inside `ns-client`.
- `capture/sniffer.py` launches `tshark` capturing on `veth-c` inside `ns-client`.
- `analysis/pcap_analyzer.py` dissects the trace to extract TCP metrics (RTT, retransmissions, throughput).

## 2. Rationale: Why Impairments and Capture Are on the Sender Side

> **Key architectural decision:** Both `tc netem` rules and `tshark` capture are applied
> to **`veth-c` inside `ns-client`** (the sender), NOT on the receiver side.

### 2.1 `tc netem` — Egress-Only Semantics

`tc netem` is a **queuing discipline (qdisc)** and operates exclusively on **egress**
(outgoing) traffic of the interface it is attached to.

When netem is applied to `veth-c` in `ns-client`:
- Every TCP data segment leaving the sender is delayed / dropped / rate-limited
  **before it reaches the wire**, exactly mirroring a real WAN link.
- The resulting RTT observed by the sender is:
  `RTT ~= 0 ms (veth loopback) + netem_delay * 2  (one-way delay, round-trip)`
- This makes experiments reproducible and the expected RTT trivially calculable.
- Placing netem on the receiver side would delay returning ACKs instead of data
  segments; the RTT estimate would still rise, but retransmission semantics (§2.2)
  would differ from a real network.

### 2.2 Capture on the Sender for Retransmission Analysis

TCP retransmissions are **generated by the sender** when:
1. The retransmission timer (RTO) fires (no ACK received in time), **or**
2. Three duplicate ACKs arrive (fast retransmit).

Because the receiver simply never sees lost packets, a `tshark` session on the
**receiver interface** would never record `tcp.analysis.retransmission` frames — those
segments are re-sent *from the sender* after loss is detected.

Capturing on `veth-c` (sender egress) gives:
- All original data segments (including those that will be lost to netem).
- Retransmitted segments (with `tcp.analysis.retransmission` expert info).
- ACKs flowing back from the receiver (visible as reverse traffic on the veth pair).
- Correct `tcp.analysis.ack_rtt` computation (needs both directions on same capture).

A receiver-side capture would make the retransmission counter always 0 under loss
scenarios — defeating the entire purpose of the experiment.

### 2.3 Summary Table

| Concern | Applied on | Reason |
|---|---|---|
| `tc netem` delay / loss / bw | `veth-c` (sender egress) | netem is egress-only |
| `tshark` packet capture | `veth-c` (sender egress) | Retransmissions originate at sender |
| RTT measurement | Sender TCP stack | Sender measures ACK round-trip |
| Integrity check (SHA-256) | Receiver (`tcp_receiver.py`) | Verifies received bytes match sent |

## 3. Experiment Pipeline

```
experiments/run_all.py
  |
  +-- For each scenario (or --scenarios filter):
  |     1. sudo -n nsrun.sh ns-client impair.sh apply <params>
  |     2. [--capture] sniffer.py -> tshark on veth-c in ns-client
  |     3. sudo -n nsrun.sh ns-server tcp_receiver.py  (background)
  |     4. sudo -n nsrun.sh ns-client tcp_sender.py    (foreground, timed)
  |     5. sniffer.stop() -> .pcap written to results/pcaps/
  |     6. pcap_analyzer.py -> extract RTT, retrans, throughput
  |     7. Append row to results/transfers.jsonl
  |     8. sudo -n nsrun.sh ns-client impair.sh clear
  |
  +-- summarize.py -> ASCII table of results
```
